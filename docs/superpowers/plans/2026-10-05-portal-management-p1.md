# Portal management P1 contract proposal

## Read-only findings

- The canonical document is the root `portals.yml`. The public template has three distinct top-level collections: `tracked_companies`, `job_boards`, and `search_queries`; this slice should manage only the first two.
- Both portal collections contain named entries and are loaded by `scan.mjs` through the same provider resolver. `enabled: false` skips an entry; omitted `enabled` is treated as enabled. The scanner requires a non-empty `name`.
- There is no persisted entry ID. `validate-portals.mjs` compares names after trim/lowercase/space-collapse, and only warns on duplicate *enabled* tracked-company names. Proposed selector identity is the composite `(collection, normalized name)`, with ambiguous duplicate names rejected. Keep `name` immutable during update; renaming can be represented as delete plus add.
- Public template fields for tracked companies: `name`, `enabled`, `careers_url`, `api`, `provider`, `scan_method`, `scan_query`, `notes`. The core validator also accepts a nested `parser` object (`command`, `script`, `args`, `timeout_ms`, `max_buffer_bytes`); the scanner's local-parser provider can execute it. The management API must never expose or accept `parser` or arbitrary command-like fields.
- Public template fields for job boards: `name`, `enabled`, `careers_url`, `api`, `provider`, `notes`, and provider-specific public settings `consider_board`, `consider_size`, `getro_collection`, `getro_max_pages`, `getro_max_age_days`, `countryCode`, `searchKeywords`, `searchLocation`, `pageSize`, `maxPages`, `siteKey`, and `cat_id` (HigherEdJobs examples are commented out). Do not assume these fields apply to tracked companies. The current validator does not validate job-board item schemas, so the API must enforce its own boundary.
- `search_queries` has its own `{name, query, enabled}` shape and remains out of this first slice. Global filters and all other YAML content must remain untouched.
- Existing URL validation allows HTTP or HTTPS and does not reject credentials or private hosts. Proposed mutations accept only absolute HTTPS `careers_url`/`api` values without URL credentials or fragments and reject obvious localhost/private literal hosts. The route performs no fetch; provider transport retains its own request-time safety checks.

## Proposed API and persistence contract

- The existing `GET /api/portals` snapshot/verification contract stays unchanged. New `GET /api/portals/entries?collection=tracked_companies|job_boards&limit=25&offset=0` returns a bounded page, canonical document SHA, and curated safe entry fields. Never return `parser` or unknown provider-specific fields; preserve them in the YAML when unrelated safe fields change.
- `GET /api/portals/entry?collection=…&name=…` resolves the normalized name within that collection and returns 404 when absent, 409 when ambiguous.
- `POST /api/portals/commands` accepts a closed command shape with UUID `operationId`, `operation: add|update|delete`, `collection`, `expectedSha256`, `confirm: true`, and exact `selector`/`entry` fields for that operation. Add uses null SHA only when the document is absent; update/delete require the current SHA. Entry name is immutable on update. Enforce normalized-name uniqueness for adds and reject ambiguous legacy names.
- Enforce the collection-specific public field allowlists above. An enabled new entry or an update that enables/changes routing must match a supported provider plus its known URL/config shape; disabled canaries may carry unknown provider IDs and project `scanSupported:false`. `websearch` projects `handoffRequired:true` but `scanSupported:false`. Preserve unknown existing YAML nodes, comments, root filters, and nested provider settings when editing an entry; omit unknown values from API responses. Existing parser/local-parser entries may be disabled or deleted but never enabled or exposed. URL validation rejects credentials, fragments, non-HTTPS URLs, localhost, and private literal addresses.
- Use fixed document path `portals.yml`, bounded request/document sizes, explicit confirmation, SHA compare-and-swap, and stable UUID payload replay/conflict behavior through the existing mutation table. No arbitrary path, shell execution, endpoint dispatch, scan, or evaluation.
- YAML aliases are kept in place for untouched content. A write that would change an aliased target shared outside the selected collection/entry/field fails with `PORTAL_SHARED_ALIAS_MUTATION` (409); unrelated aliases do not block scoped edits.

### Implemented field and page bounds

- All entry mutations share `name` (required on add; trimmed string, max 180 chars), `enabled` (boolean), `careers_url` and `api` (absolute HTTPS strings, max 2,048 chars), `provider` (lowercase slug, max 64 chars), and `notes` (max 4,000 chars). `scan_method` accepts only `websearch`; `scan_query` is max 2,000 chars and is handoff metadata only.
- Job-board-only text fields: `consider_board` (500 chars), `countryCode` (allowlisted two-letter code), `searchKeywords` (2,000), `searchLocation` (500), and `siteKey` (500). Provider-backed operational caps: `pageSize` ≤100, `maxPages` ≤20, `getro_max_pages` ≤200 (provider hard ceiling), `getro_max_age_days` 0–3,650, and `consider_size` ≤2,000. Numeric identifiers `getro_collection` and `cat_id` are capped at 999,999,999 and 100,000 respectively.
- Sensitive URL query keys, URL userinfo, fragments, non-HTTPS schemes, non-default HTTPS ports, localhost/private literal hosts are rejected on writes. Reads omit credential-bearing or malformed URL fields and mark them in `redactedFields`; those hidden values remain unchanged if omitted from a partial update.
- List default is 25; limit is 1–100 and offset 0–10,000. Portal content is capped at 512,000 bytes before egress; command JSON is capped at 16,384 bytes before parse.
- Current explicit provider/url recognition is intentionally partial: greenhouse, lever, ashby, and workday ATS host mappings; job-board-specific SolidJobs divisions, JustJoin, NoFluffJobs, Getro with collection ID, Consider with board ID, Jobstreet with an allowlisted API host/path and site/search fields, Glints with an allowlisted API host/path/country/keywords, Joinup, and HigherEdJobs with category ID. Other built-in and plugin providers remain disabled canaries with `scanSupported:false` until matcher/config parity is added. For example, iCIMS postings can still be managed but cannot be enabled through this slice. Websearch carries `handoffRequired:true` but remains unsupported by the hosted zero-token scan worker.

## Required implementation files and dependency

- Add `web/src/lib/cloud-portal-management.mjs` and fixed route handlers under `web/src/app/api/portals/entries`, `/entry`, and `/commands`; preserve the existing `/api/portals` handlers.
- Add only exact method/path rules in `web/src/proxy.ts`.
- Add `yaml` as a direct `web` dependency and update its lockfile. `js-yaml` is already used but is a native-object parser; it is not installed with a comment-preserving Document/CST editing API. The official `yaml` package documents `parseDocument()` and a `Document` API for comments and aliases: [YAML Document API](https://eemeli.org/yaml/#documents).
- Add focused tests for both collection schemas, pagination, safe field projection, comment/filter/nested-config preservation, malformed/ambiguous identities, explicit confirmation, CAS, replay and payload conflict, and proof that no scan/provider dispatch occurs.

## Decision needed before implementation

Design confirmed: use natural-key identity (collection + normalized name, immutable on update) and a safe read projection (curated fields only, with opaque/unknown provider values preserved but not returned). The template has no stable entry IDs, and existing tracked-company provider configuration is intentionally open-ended.

## Implementation and verification status

Implemented the cloud service and fixed authenticated routes. The legacy `GET /api/portals` and `POST /api/portals` contracts remain unchanged. List/detail expose only allowlisted fields and computed `enabled`, `scanSupported`, `handoffRequired`, `identityAmbiguous`, `hasOpaqueSettings`, and `redactedFields` flags; provider capability is recognized only for matched known host/config combinations, without importing or invoking providers. Credential-bearing or malformed legacy URLs are omitted from responses and omitted update fields preserve them in YAML. Alias references that would cause a selected collection, entry, or touched field to change elsewhere are rejected; unrelated aliases remain editable. Focused synthetic tests pass for both collections, comment/filter/opaque-node preservation, URL and parser restrictions, alias scope, duplicate identities, key-order replay/conflict, stale SHA, write-race rollback, and JSON MIME validation. No scan or provider fetch is invoked. No full build, deployment, or production database write was run.

Dependency note: the current locked `next@16.3.4` is in the affected range for [GHSA-vcvr-r3jv-pc5j](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j), a critical Node `next/og` `ImageResponse` RCE fixed in 16.3.6+. The current `web/src` tree has no `next/og` or `ImageResponse` usage, so this review found no app-level vulnerable route; this is not a general security conclusion. The YAML dependency is not implicated. Next remains unchanged in this portal slice; handle its patch separately.
